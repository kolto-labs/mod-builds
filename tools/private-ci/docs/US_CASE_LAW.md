# United States copyright analysis: purchased KOTOR files in automated mod tests

Research date: 2026-10-14. Jurisdiction: United States. This is a source-based risk analysis, not a legal opinion guaranteeing a particular license or deployment. No game was downloaded, no publisher was contacted, and no credentials were used for this research.

## Practical conclusion

Testing an independently written mod installer against a legitimately acquired game, privately, without distributing the game or bypassing access controls, has a substantially better legal posture than distributing complete patched installations or offering public cloud gameplay. There is no general US rule that buying a game grants unlimited copies on third-party cloud runners, nor an appellate holding specifically approving this KOTOR/GitHub Actions arrangement. The actual game EULA, storefront agreement, permitted number and locations of installations, authorized user, and applicable circuit matter.

The clearest path is an owner-controlled runner with the owner's licensed local installation, a public workflow testing the public mod-build guide, and public output limited to authored code plus terse test results. A public GitHub repository can orchestrate a private machine; public orchestration does not require publishing all inputs. Hosted acquisition of a full game can be considered after verifying the relevant license permits that installation and automated use, preferably with written publisher confirmation if permission is unclear. DRM-free GOG acquisition reduces technical access-control risk; it does not eliminate copyright, EULA, or storefront restrictions.

## Statutory rights and defenses

* [17 USC §106](https://www.law.cornell.edu/uscode/text/17/106), especially (1), (2), (3), (4), and (5): reproduction and preparation of derivatives are separate from distribution and public performance/display. A private cloud disk copy may implicate reproduction even when there is no public distribution. Public screenshots, dialogue dumps, cutscenes, and sound recordings raise additional issues independent of the private test run.
* [17 USC §107](https://www.law.cornell.edu/uscode/text/17/107): research and scholarship are examples, not automatic exemptions. All four factors apply: purpose/character, nature, amount/substantiality, and market effect. Functional parser interoperability, minimal necessary copied inputs, no substitute playable distribution, and private retention support a stronger argument. Copying the entire highly creative game for repetitive compatibility testing is not automatically fair because the project is unpaid or called research.
* [17 USC §117(a)](https://www.law.cornell.edu/uscode/text/17/117): the **owner of a copy of a computer program** may make or authorize another copy/adaptation if it is an essential step in utilization with a machine and used in no other manner, or for archival purposes subject to destruction when possession ceases to be rightful. It is not a blanket license for any purchaser, any purpose, or all separable audiovisual assets. Under §117(b), transferring adaptations requires copyright-owner authorization. Under §117(c), maintenance/repair is a narrow provision, not a general CI exception.
* [17 USC §1201(a), (b), (c), and (f)](https://www.law.cornell.edu/uscode/text/17/1201): circumventing effective access controls and trafficking circumvention technology are distinct issues. §1201(c)(1) preserves infringement defenses such as fair use; this does not automatically make circumvention itself lawful. §1201(f) is constrained to lawfully obtained use rights, necessary/non-readily-available functional interoperability analysis of independently created programs, and noninfringing conduct. Ordinary authentication through an authorized Steam account is materially different from bypassing authentication, Steam Guard, DRM, or license enforcement.

Copyright exceptions, contract compliance, storefront account rules, and GitHub compute rules must each be assessed separately. A copyright fair-use argument does not itself authorize breaching every accepted contract or GitHub's service terms.

## Distinguishing proposed architectures

1. **File-only tests on an existing licensed personal installation:** no new external installation and no public gameplay are necessary. Read/parse/mod/write operations can still be reproduction/adaptation, but authorization for ordinary personal installation/mod use and any statutory defense are easier to assess. Isolate copied test output and delete it after verification. Baselines/checkpoints contain game bytes and must remain private too.
2. **Ephemeral hosted-runner installation downloaded directly through the purchaser's authenticated storefront:** potentially lawful if that authorized user can install/use this copy in that location for this purpose under game/store terms. The public repository does not magically make the working directory public, but it does not confer a license. Parallel OS/game jobs can create multiple copies and concurrent-use issues. Credentials may constitute sensitive account access; do not share them with unrelated contributors or untrusted pull requests.
3. **Private storage of purchased installers for the owner to fetch into a private test runner:** private access and encryption improve privacy, not underlying authorization. Check backup, installation, transfer, and third-party hosting permission. This may avoid repeated storefront credential handling while leaving copy/license questions intact.
4. **Public archive of an encrypted whole game with a secret key kept private:** not recommended as a legal/privacy shortcut. §101 copies can embody works perceivable/reproducible with a machine; encryption is not a statutory exclusion. Producing and hosting the archive creates copy questions. Whether a particular transfer to the public constitutes §106(3) distribution when recipients lack keys is fact-dependent and not resolved by the reviewed cases. It would be overclaiming to declare every ciphertext upload infringing, and equally wrong to declare it lawful simply because the key is secret. Keep complete originals and derivative trees out of public git, Actions artifacts, caches, release assets, and logs.
5. **Executing the game privately for smoke testing:** adds licensed execution/RAM-copy issues; no public performance necessarily follows merely because the machine is remote. Owner-only automation is unlike a publicly accessible game-streaming service. Publicly streamed gameplay or screenshots introduce separate performance/display, license, and publisher content-policy questions. Do not bundle audiovisual capture into public evidence by default.
6. **Shipping code, mod instructions, or patch recipes:** ordinarily safer than distributing complete game trees, but no-original-byte recipes may still implicate derivative expression under Micro Star. Verify each actual mod's permissions and exclude proprietary files. Independent format tooling and hashes/counts/status summaries carry much lower asset disclosure risk.

## Recommended implementation boundary

Use separate public **synthetic/open-fixture** jobs and opt-in owner-only **licensed-baseline** jobs. Public guide CI should have a genuine guide validation purpose, not merely relabel unrelated private compute. For licensed jobs, prefer an owner-controlled self-hosted runner and a preinstalled legally acquired baseline; allow a storefront acquisition adapter only where that purchaser's terms support it. Keep executable game launch an explicit separate mode from installer validation. Authenticate normally, preserve Steam Guard, do not crack or patch access controls, never support anonymous proprietary downloads, and do not make an account available to other users.

Restrict secrets and licensed jobs to trusted protected branches/manual dispatch and prevent unreviewed workflow/scripts from handling credentials or assets. Pin the tested private-code commit, keep stdout sanitized, and publish only checks/counts/timing plus hashes if desired. Disable uploading complete directories, archives, checkpoints, raw logs, crash dumps, and gameplay images. Clear the ephemeral working copy and fail closed on accidental asset export. These are privacy safeguards; they do not cure an impermissible license use.

A narrow publisher clarification would settle the biggest unknown efficiently: permission for one purchaser to install KOTOR/KOTOR II on isolated ephemeral CI machines solely to validate personally applied mods, with no public distribution, no public gameplay service, no DRM circumvention, and limited concurrency. GOG's DRM-free offering may be operationally preferable, but purchase should follow actual KOTOR license review rather than assumed broader rights. GitHub's authorization for genuine public guide tests should be determined independently from game licensing.
